# 重构基线与迁移计划

更新时间：`2026-05-01`

这不是“推倒重写”方案，而是一份面向现有仓库的渐进式重构基线。目标是先把边界立起来，再按业务切片迁移，避免在继续迭代功能时把复杂度继续堆进巨型文件。

## 1. 为什么现在必须重构

当前仓库已经具备最小可用闭环，但结构上出现了几个明显的扩张点：

- 前端存在多个超大页面文件。
  例如 `SkillManagementPage.vue`、`SampleExecutionPage.vue`、`SecurityEventsPage.vue`、`AiEndpointsPage.vue` 都同时承担了数据获取、状态机、表单规则、动作编排和页面渲染。
- 前端共享层过厚。
  `frontend/src/services/api.ts` 已经成为单体 API 文件，`frontend/src/style.css` 也已经承担了几乎所有页面样式。
- 后端执行链耦合较重。
  `task_runner.py` 和 `policy_enforcer.py` 之间已经出现了不合理的方向依赖，`policy_enforcer.py` 直接引用了 `task_runner.py` 的内部函数。
- 后端路由和服务的职责边界不够清晰。
  `skills.py`、`tasks.py` 等路由文件仍然偏胖，业务逻辑、DTO 组装、状态推进和审计动作没有完全分层。
- 数据模型仍然集中在 `models.py`。
  对持续扩展不友好，也不利于后续拆分迁移或引入 Alembic。

结论很直接：这个项目已经过了“继续往单文件里塞东西还能维持效率”的阶段。

## 2. 本次重构的目标

本轮不追求一次性改完，而是建立后续可复制的结构模板：

1. 前端从“按页面堆逻辑”改成“按 feature 组织”。
2. 后端从“按技术层堆文件”逐步改成“模块化单体”。
3. 页面文件只做装配，复杂状态放进 composable 或 service。
4. 后端执行链的策略判断、授权判断、任务执行必须解除反向依赖。
5. 文档必须能够反映真实目录和迁移状态，而不是只写理想方案。

## 3. 目标结构

### 3.1 前端目标结构

```text
frontend/src/
├─ app/                        # 应用级入口、路由装配、全局 providers
├─ shared/
│  ├─ components/             # 通用展示组件
│  ├─ composables/            # 通用组合式逻辑
│  ├─ services/               # http client、auth、time、redaction
│  └─ styles/                 # design tokens、layout、utility
├─ features/
│  ├─ ai-endpoints/
│  │  ├─ components/
│  │  ├─ constants.ts
│  │  ├─ helpers.ts
│  │  └─ useAiEndpointsPage.ts
│  ├─ skills/
│  ├─ sample-execution/
│  ├─ security-events/
│  └─ defense-config/
└─ pages/                     # 薄路由入口，只负责拼 feature
```

前端的核心原则：

- `pages/` 只保留页面装配。
- `features/` 负责一个完整业务面的状态和 UI。
- `services/api.ts` 未来拆成 `shared/services/http.ts` + 各 feature 自己的 API 文件。
- `style.css` 未来只保留全局 token、基础布局和通用 utility，页面或 feature 的细节样式逐步下沉。

### 3.2 后端目标结构

```text
backend/app/
├─ platform/                  # config、db、logging、security、response
├─ modules/
│  ├─ auth/
│  ├─ ai_endpoints/
│  ├─ skills/
│  ├─ tasks/
│  ├─ security_events/
│  ├─ defense_policy/
│  └─ reports/
├─ integrations/              # model provider、mail、runtime gateway
├─ workers/                   # task worker、queue adapter
└─ main.py
```

后端的核心原则：

- 路由只负责请求解析、鉴权挂载和响应输出。
- 模块 service 负责业务编排。
- repository 负责数据库访问。
- policy / authorization / execution 各自有明确边界，禁止互相调用对方的“私有辅助函数”。
- 与外部模型、邮件、运行时回传相关的能力统一归到 `integrations/`。

## 4. 当前已经识别出的硬问题

### 4.1 前端

- `frontend/src/pages/SkillManagementPage.vue`
  文件过大，既负责表单元数据解析，又负责导入预览、扫描任务回显、分页、状态反馈。
- `frontend/src/pages/SampleExecutionPage.vue`
  承担样本筛选、任务创建、批量执行、目标路由选择、运行态回显，已经是一个复合工作台。
- `frontend/src/services/api.ts`
  类型和请求都堆在一个文件里，后续每加功能都要继续膨胀。
- `frontend/src/style.css`
  已经变成全项目样式总汇，不利于维护和定位。

### 4.2 后端

- `backend/app/services/task_runner.py`
  同时承担规则评估、AI 审核、事件生成、报告归档、Skill 扫描联动。
- `backend/app/services/policy_enforcer.py`
  当前依赖 `task_runner.py` 内部函数，这说明“前置授权”和“最终执行判定”还没有抽成独立策略层。
- `backend/app/api/routes/skills.py`
  路由文件承担了过多编排逻辑。
- `backend/app/models.py`
  单文件模型继续增长后会越来越难维护。

## 5. 本次已完成的第一刀

本轮已经把 `AI 目标` 页切成了第一条 feature 化样板：

- 新增 `frontend/src/features/ai-endpoints/constants.ts`
- 新增 `frontend/src/features/ai-endpoints/helpers.ts`
- 新增 `frontend/src/features/ai-endpoints/useAiEndpointsPage.ts`
- 新增 `frontend/src/features/ai-endpoints/components/AiEndpointDrawer.vue`
- `frontend/src/pages/AiEndpointsPage.vue` 收缩为页面装配层

这条切片的意义不是“只优化一个页面”，而是把以后迁移其它页的模板先跑通：

- 页面主文件负责布局和模块拼装
- 复杂状态、批量动作、表单载荷构建放进 composable
- 大块子界面先独立成 feature 组件
- 常量、文案映射、辅助函数脱离页面本体

## 6. 后续迁移顺序

建议按收益和风险排序推进：

1. `SkillManagementPage.vue`
   价值最高，当前最臃肿，且已经具备“动作清单 + 结果区块”的天然 feature 边界。
2. `SampleExecutionPage.vue`
   迁移为 `sample-execution` feature，拆开样本筛选、目标路由、任务回显。
3. `SecurityEventsPage.vue` 与 `SecurityEventReportPage.vue`
   拆为事件列表 feature 和报告详情 feature。
4. `frontend/src/services/api.ts`
   拆为共享 http client + feature API。
5. `backend/app/services/task_runner.py` / `policy_enforcer.py`
   抽出独立策略评估层，消除反向依赖。
6. `backend/app/api/routes/skills.py` / `tasks.py`
   引入模块 service，收薄路由层。

## 7. 对后端执行链的明确改造建议

后端下一步最值得先动的不是 UI，而是把执行链分三层：

### 7.1 Strategy Evaluation

负责：

- 规则命中
- 风险分值
- 命中信号
- 推荐判定

输出统一的 `PolicyAssessment`。

### 7.2 Authorization Gate

负责：

- 结合受保护路径 / 技能 / 插件
- 结合控制项模式 `enforce / observe / off`
- 产出 `allow / review / deny`

输入是 `PolicyAssessment`，不再自己回头调用任务执行器内部函数。

### 7.3 Execution Orchestrator

负责：

- 调 Provider
- 写原始响应
- 生成事件
- 导出报告

只消费已完成的评估结果，不再重复评估。

## 8. 重构完成的判定标准

达到以下条件，才算这轮“架构真正改了”，而不是只换目录：

- 页面文件长度明显下降，只承担装配职责。
- feature 目录能独立容纳自己的状态、常量、组件和 API。
- 后端执行链不再出现 service 之间反向引用私有函数。
- 单个文件继续增长时，不需要再回到“把逻辑塞回页面/路由”的老路。
- 文档能直接告诉后来者“现在的结构是什么、下一刀应该切哪里”。

## 9. 当前建议

如果继续往下做，最合理的顺序是：

1. 先迁 `SkillManagementPage.vue`
2. 再拆 `frontend/src/services/api.ts`
3. 然后处理后端 `task_runner` / `policy_enforcer` 的策略层分离

这样收益最大，也不会一上来就把全项目同时打散。
