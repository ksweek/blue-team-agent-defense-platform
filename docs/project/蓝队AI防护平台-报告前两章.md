# 蓝队 AI 防护平台项目报告（前两章）

> 说明：本文章节结构参照 `file/竞赛作品报告.pdf` 的前两章组织方式整理，内容基于本仓库当前实现、项目文档与前后端页面能力归纳而成，并补充了公开官方资料作为背景依据与置信度说明。

## 第一章 作品概述

### 1.1 背景及研发意义

随着大模型能力从单轮问答逐步扩展到检索增强、代码执行、浏览器操作、插件调用、MCP 工具调用与多步 Agent 编排，AI 系统面临的安全边界已经发生明显变化。过去很多系统只需要关注“模型回答得对不对”，现在还必须关注“模型是否会在错误指令引导下调用不该调用的工具、读取不该读取的路径、输出不该输出的敏感信息、形成无法审计的自动化行为链”。这意味着，AI 安全问题正在从“模型内容风险”演变为“接入、调用、运行时、审计、治理”一体化的工程问题。

从项目落地实践看，当前很多团队在接入 AI 或 Agent 时，往往优先解决“怎么连上模型”这一问题，而不是优先解决“连上之后如何统一纳管”。一旦业务系统同时接入多个模型、多个 Agent 或多个运行时客户端，常见问题会迅速暴露出来：上游地址和密钥分散在不同脚本、环境变量和页面表单中；请求可能直接打到模型侧，缺乏统一网关；安全规则、技能名单、敏感目录策略无法按目标隔离；出现异常后只能翻日志，难以形成完整证据链。对蓝队、防护团队与安全运营团队而言，这类碎片化接入方式会显著提高治理成本。

本项目的研发意义正在于此。蓝队 AI 防护平台并不试图替代大模型或 Agent 本身，而是作为一层前置的安全网关与管理平台，解决“AI 接入之后如何统一治理”的问题。其核心价值包括以下几个方面：

1. 将分散的 AI 接入方式收敛到统一平台入口，实现统一接入、统一审查、统一留痕。
2. 将传统只针对 Web 或 API 的安全防护思路扩展到 AI/Agent 场景，覆盖提示词输入、工具调用、技能执行、敏感路径访问和运行时回传等链路。
3. 将“每个接入的 AI 单独治理”作为基本设计原则，使不同目标可以拥有独立的保护策略、技能扫描范围、敏感目录保护规则和辅助研判策略。
4. 将攻击测试、安全事件、报告导出、审计记录和运行时注册纳入同一平台闭环，提升可验证性、可追溯性与可运营性。

因此，本项目的意义不在于再做一个“聊天页面”，而在于构建一套面向生产接入场景的 AI 防护基础设施。它既服务于模型安全，也服务于平台安全、运行时安全和运维审计，是 AI 从可用走向可控、可审、可验证的重要工程支撑。

### 1.2 国内外现状

#### 1.2.1 国内现状

国内生成式人工智能应用已经进入加速落地阶段，监管和产业化两条主线正在并行推进。一方面，生成式人工智能服务备案、登记与配套治理要求持续完善，说明模型能力、API 能力和基于备案模型构建的应用正在快速增长。根据国家互联网信息办公室 2026 年 3 月 17 日发布的《关于发布生成式人工智能服务已备案信息的公告（2026 年 1 月至 2 月）》，截至 2026 年 2 月 28 日，累计已有 796 款生成式人工智能服务完成备案，481 款生成式人工智能应用或功能完成登记。另一方面，伴随更多单位将 AI 能力接入业务流、客服流、研发流和自动化运维流，接入后的安全治理需求也在同步上升。

从政策与治理导向看，国内对生成式人工智能的关注重点已经不再停留于“是否能用”，而是进一步强调“如何在可控边界内使用”。公开监管文件持续强调安全评估、数据与个人信息保护、权限控制、风险识别和责任边界。尤其当一个平台同时聚合多个模型、多个智能体能力、多个第三方接口时，权限管理、最小暴露、风险发现和审计闭环就不再是可选项，而会直接决定系统能否稳定投入生产。

从工程实际看，国内不少 AI 平台或业务系统已经具备模型接入能力，但仍普遍存在以下不足：第一，接入流程偏向“能调用即可”，缺少统一的注册、激活、长期凭据换取与本地复用流程；第二，很多系统只提供全局级配置，缺少面向单个 AI 目标的细粒度治理；第三，攻击测试、技能扫描、敏感目录保护和安全事件之间往往彼此分散，难以形成平台级联动。这正是本项目需要补位的现实空间。

#### 1.2.2 国外现状

国外在 AI 安全治理方面的研究和工程实践起步较早，正在逐步形成“风险框架 + 场景分类 + 落地控制”的发展路径。以 OWASP 为代表的社区侧规范，已经将 Prompt Injection、Sensitive Information Disclosure、Excessive Agency 等问题纳入 LLM/Agent 的核心风险视图；以 NIST 为代表的标准侧框架，则强调通过治理、映射、测量和管理等方法，持续控制 AI 系统全生命周期风险。

尤其值得注意的是，随着 Agent 系统快速发展，国外安全研究已不再把风险仅仅理解为“模型输出错误”，而是开始把工具调用、任务委派、环境交互、权限边界和上下文污染纳入一个更完整的威胁模型中。NIST 针对 Agent Tool Use 的公开材料也表明，实际系统中的“工具使用”已经成为需要单独识别、分类和治理的风险面。这与本项目中围绕 Skill、工具、插件、敏感路径、运行时命令和 OpenClaw WebSocket 交互所做的设计方向高度一致。

总体来看，国内外在 AI 安全方面已经形成一个共识：单纯依赖模型厂商侧安全能力并不足以覆盖业务落地场景，真正进入生产环境后，仍然需要一层靠近业务接入面的安全平台，负责接入治理、运行时审查、攻击验证和事件留存。本项目就是顺应该趋势而设计的一套平台化实现。

### 1.3 传统 AI 接入防护方式与现有方案局限

在很多早期 AI 项目中，系统通常通过最直接的方式接入模型：在脚本、环境变量或页面表单中填写上游 API 地址与密钥，然后由业务代码直接调用模型接口。这种方式在单模型、单开发者、单环境阶段尚可工作，但在面向实际运营时会暴露出明显短板。

首先，传统接入方式往往只有“调用链”，没有“治理链”。请求是否应该放行、是否触发敏感路径保护、是否命中提示词注入规则、是否需要辅助研判，往往无法在统一入口中决策。其次，很多系统只有全局级别配置，没有面向单个 AI 目标的策略隔离能力，这意味着一个目标的敏感路径、技能清单或风险模式，很难独立配置而不影响其他目标。再次，传统方案多数只关注 HTTP 请求，不重视 Agent 运行时与 WebSocket 通信场景，导致类似 OpenClaw 这类控制台/运行时模式很难被真实纳入审查。最后，很多项目虽然能记录日志，但无法把“攻击样本 -> 请求 -> 审查结果 -> 上游响应 -> 安全事件 -> 安全报告”串成闭环。

如果继续沿用上述方式，平台在规模稍大后通常会出现三个问题：一是配置越来越多，但责任边界越来越模糊；二是风险越来越集中，但证据链越来越零散；三是功能越来越丰富，但可验证性越来越差。因此，单纯的“模型转发器”或“通用 API 代理”已经不足以满足 AI 安全防护需求，必须演进为具有目标治理、运行时审查、事件归档与攻击验证能力的平台系统。

### 1.4 产品创新综述

结合当前仓库实现，本项目的创新点主要体现在以下几个方面。

1. 采用“统一入口 + 运行时审查”的平台设计。平台不仅接管传统 HTTP/API 请求，还扩展到 Runtime 注册、授权、心跳、完成回传等链路，使防护从静态配置前移到运行时行为治理。
2. 采用“短期激活码换长期凭据”的客户端接入机制。管理员预先在平台创建 AI 目标并生成短期接入激活码，客户端首次接入只需填写管理端地址、上游地址、上游令牌和激活码，即可换取长期 Runtime 凭据，后续本地复用，兼顾易用性与凭据暴露控制。
3. 采用“按 AI 目标单独治理”的管理方式。每个接入目标都可以独立配置接入协议、防护模式、受保护路径、受保护技能、辅助研判策略、注册码和 Runtime 绑定关系，避免所有目标共用一套粗粒度策略。
4. 将 Skill 扫描、敏感目录保护、攻击实验室、安全事件和报告中心整合到同一平台闭环中，实现从防护前置到事后追溯的全链路联动。
5. 针对 OpenClaw 场景提供专门兼容路径。平台不仅支持通用 AI 接口治理，还实现了面向 OpenClaw WebSocket 消息的保护桥接，使聊天消息、工具调用消息和运行时命令能够真正经过平台审查，而不是停留在概念层面。
6. 支持系统级“辅助研判 AI”配置，并允许在单个受保护目标维度选择是否启用，从而形成“被保护 AI”与“负责研判的 AI”相互分离的生产化架构。
7. 引入 Redis 优先缓存、入口限流、请求体大小限制、安全响应头、敏感字段脱敏和 Guard Trace 报告视图，使平台自身也具备可验证的安全加固与性能治理基础。

综上，本项目的创新重点不是单一算法，而是把 AI 安全从零散功能点整合为一套可接入、可运营、可验证、可审计的平台体系。这种创新更偏工程化和体系化，适合真实部署、联调和逐步扩展。

## 第二章 需求分析

### 2.1 功能需求

结合本项目当前架构与页面能力，平台至少需要满足以下功能需求。

#### 2.1.1 AI 目标接入与生命周期管理

平台需要支持多个 AI 目标的统一纳管，包括目标创建、编辑、启停、默认路由设置、协议类型选择、上游地址配置、API Key 管理以及目标分组展示。同时，平台应当把每一个接入目标明确显示出来，避免目标隐藏在环境变量或脚本参数中，便于后续逐个治理。

#### 2.1.2 Runtime 注册、激活与长期凭据复用

平台需要支持客户端 Runtime 的注册与绑定能力，特别是要支持“管理员生成短期激活码，客户端一次性交换长期凭据”的接入流程。该流程的目标是减少管理员分发长密钥的风险，同时降低客户端重复填写配置的成本。首次接入成功后，本地应能复用已换取的长期凭据，后续直接连接，不再要求重复输入过多信息。

#### 2.1.3 统一代理入口与运行时审查

平台需要在 AI 请求进入上游系统前，提供统一代理入口，并支持在运行时执行审查、授权和回传。对于传统 HTTP 型 AI 接口，需要支持统一代理、规则检查和路由转发；对于类似 OpenClaw 的控制台/运行时形态，需要支持 WebSocket 层消息代理、`sessions.send` 类聊天消息检查，以及工具调用类消息检查。只有这样，平台才能真正覆盖“AI 聊天”和“AI 调工具”两类核心风险面。

#### 2.1.4 按目标进行策略治理

平台需要支持基于单个 AI 目标的细粒度防护配置，而不是只提供全局规则。具体包括：受保护路径、受保护技能、受保护插件、目标独立的防护模式、默认保护策略继承与局部覆盖，以及是否启用辅助研判等。对于实际运营场景而言，“按目标治理”比“全局一刀切”更符合多业务、多环境、多能力源接入的现实需求。

#### 2.1.5 Skill 扫描与敏感目录保护

平台需要把 Skill 扫描与敏感目录保护整合到 AI 目标维度。也就是说，扫描的对象、保护的目录、受信任与待审批的 Skill、以及与路径访问相关的高风险行为，都应当围绕具体目标展开，而不是作为孤立功能存在。这样既能减少无关噪声，也便于把扫描结果直接转换为目标治理动作。

#### 2.1.6 攻击实验室与效果验证

平台需要提供独立的攻击实验室能力，使管理员或安全测试人员能够选择某一类攻击集、选择某一个受保护 AI 目标，并发起真实攻击测试。测试完成后，平台应明确展示哪些任务正在运行、哪些已经结束、哪些已触发拦截或告警，并能够把相应结果沉淀到安全事件与报告中。对于 OpenClaw 等目标，还应确保攻击不是“打到假接口”，而是真正通过运行时桥接路径命中目标系统。

#### 2.1.7 安全事件、报告与审计闭环

平台需要把规则命中、辅助研判结果、人工处置、攻击测试结果和上游响应沉淀为统一的安全事件记录，并进一步生成可阅读、可导出、可回看的安全报告。同时，系统设置、动作执行、配置变更和关键接入行为也需要保留审计记录，形成完整证据链。

#### 2.1.8 系统设置与辅助研判 AI 配置

平台需要提供系统级设置入口，用于统一配置基础参数、运维动作、通知能力以及辅助研判 AI 的接口地址、API Key 和模型名称。与此同时，每个被保护目标页面应提供清晰入口，用于选择是否启用该辅助研判能力。这样可以保证研判能力集中配置、按目标启用，既减少配置冗余，也更符合生产架构中的角色分离原则。

### 2.2 非功能需求

除核心功能外，平台还需要满足以下非功能需求。

#### 2.2.1 安全性

平台本身就是安全系统，因此其首要非功能需求就是安全性。系统需要保证管理端认证、角色权限控制、运行时凭据校验、短期激活码有效期控制、长期凭据本地复用边界控制，以及导出/备份场景下的敏感字段脱敏。同时，对外展示的页面和日志信息也需要避免无意暴露高敏感数据。当前实现已经覆盖登录与公开注册限流、Trusted Host、安全响应头、请求体大小限制、WebSocket 消息大小限制、验证错误脱敏和报告展示字段脱敏等基础加固能力。

#### 2.2.2 可靠性

平台需要在持续运行中保持稳定，至少应支持后端服务、前端页面、任务执行器、运行时桥接器的基本协同工作，并在常见异常场景下给出可理解的错误反馈。对于攻击任务、运行时命令和事件生成流程，系统需要具备明确状态流转，而不是出现静默失败。当前本地测试已收集 `57` 个后端用例，完整执行结果为 `56 passed, 1 failed, 4 warnings`；唯一失败来自 SQLite 在 100 并发写入下出现 `database is locked`，说明高并发验证需要 PostgreSQL 与 Redis 支撑。

#### 2.2.3 可扩展性

平台需要具备面向多模型、多 Agent、多接入协议扩展的能力。当前项目已经涉及通用 AI 接口、Runtime 链路和 OpenClaw WebSocket 场景，后续还可能接入更多协议类型、更多规则引擎和更多外部研判服务。因此，系统设计必须允许在不推翻整体框架的情况下继续扩展目标类型、攻击集类型和辅助能力。

#### 2.2.4 可观测性与可审计性

AI 防护平台如果不能观察和回放关键行为，其价值会大幅下降。因此，系统必须具备较强的可观测性，能够对请求进入、策略命中、运行时心跳、攻击任务执行、审查决策、事件生成与报告导出等关键节点留痕。与此同时，审计信息应当面向运维和安全人员可读，而不是只有原始杂乱日志。

#### 2.2.5 易用性与可运维性

平台的目标用户并不只有开发者，还包括管理员、蓝队人员、安全测试人员与分析人员。因此，页面结构必须符合使用逻辑，关键操作应尽量少填、少跳转、少重复输入。尤其在客户端接入阶段，注册脚本必须做到首次接入可完成、二次运行可复用，降低使用门槛。对平台运维而言，系统设置、动作执行、导出与备份入口也应足够清晰。

#### 2.2.6 可维护性

随着规则、目标、攻击集和接入协议不断增加，平台需要保持较好的可维护性。具体包括：前后端模块边界清晰、配置来源明确、规则与事件字段可追踪、系统设置具备字段元数据驱动能力、文档能够覆盖接入和运维主链路。只有保持良好的代码与文档结构，平台才能持续演进，而不是在功能增加后迅速失控。
