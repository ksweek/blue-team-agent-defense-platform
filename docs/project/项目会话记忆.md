## 1. 项目当前定位

当前项目已经不再是纯 UI 原型，而是一个可本地运行、可 Docker 部署的蓝队 AI 防护平台 Beta，目标聚焦在：

- Agent / LLM 安全联调
- 攻击样本回归验证
- 防御策略治理
- 运行时审计与事件留痕
- 在线 AI 流量统一代理与 Runtime 联动

当前最小可用闭环已经具备：

1. 选攻击样本
2. 创建单个或批量任务
3. 后台 Worker 执行任务
4. 调用模型 / Agent Provider
5. 记录原始响应
6. 生成安全事件
7. 归档并下载报告
8. 通过 `/gateway/v1/*` 和 `/gateway/v1/ws/*` 纳管在线 AI 请求
9. 通过 Runtime / MCP Ticket 链路纳管外部执行器

## 4. 已经固定下来的产品与交互原则

这些不是临时偏好，而是历史会话里已经反复确认过的设计约束，后续改动应尽量沿着这套规则走：

- 页面语言以中文为主，去掉不必要的英文标签
- 去掉大段解释性文字，只保留必要提示
- 整体风格向高密度安全控制台靠拢，而不是营销式仪表盘
- 防御配置、系统设置等编辑页默认自动保存
- 动作型页面统一使用即时反馈模型，不再要求用户二次确认保存
- 顶部统一使用 `TopStatusRail` 承载 `saving / saved / error` 类状态
- 区块统一围绕 `PageSection` 组织，逐步压缩成横向操作条 + 高密度列表
- 表单控件尽量由后端元数据驱动，避免前端维护 `select / toggle / tone / helper_text` 的本地映射

## 5. 多 AI 接入与 AI 审核模式的会话结论

### 5.1 多 AI 管理

平台已经朝“同一套防护治理多 AI / 多 Agent 目标”的方向演进，当前结论是：

- 不再只依赖根目录 `.env` 中的单一 Provider
- 每个 AI 目标都可以单独接入、分组、启停保护、设置默认路由
- 样本执行时可以显式选择目标，也可以自动回退到默认路由

### 5.2 AI 二次审核三种模式

历史会话中已经确认了三种模式与名称：

- `规则直断` `rules_only`
  只跑现有规则链，命中后直接处理，不走 AI 二次审核。
- `疑似复核` `suspicious_review`
  明确攻击直接拦截，只有“可疑但不够确定”的请求交给 AI 复核。
- `剩余全审` `review_all_remaining`
  明确攻击直接拦截，除此之外的剩余请求全部进入 AI 复核。

这三种模式当前已经进入后端模型、接口返回和前端配置页。

## 8. 当前真实边界

项目已经可运行，但还没有到生产级：

- Worker 支持嵌入式与外置形态，但仍以数据库轮询为主，尚未演进到 Redis / RabbitMQ 这类独立队列
- 还没有 Alembic 迁移体系
- Provider 抽象和网关兼容入口已经形成，但不同 Provider 的响应协议、错误码和成本统计仍需继续归一
- 部分系统动作仍偏平台内模拟执行
- 报告能力已支持 JSON / HTML / DOCX 与批量打包，但还没有 PDF、签章流转和对象存储归档
- 本地 SQLite 在高并发写入下会出现锁竞争，生产级并发验证需要 PostgreSQL + Redis
