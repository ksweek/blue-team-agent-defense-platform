# 蓝队防御平台工程设计

本文档聚焦当前代码仓库的真实工程结构、职责划分和演进方向。

截至 `2026-06-20`，项目已经具备完整的前后端原型、数据库落库、JWT/RBAC、统一日志、后台 Worker、多 Provider 配置、统一网关、Runtime 注册激活、MCP 票据、Redis 优先缓存、安全加固和任务/事件/报告闭环。

## 1. 总体架构

当前工程采用前后端分离结构：

```text
Frontend (Vue 3 + TypeScript + Vite)
        |
        | HTTP / JSON + JWT
        v
Backend (FastAPI + Pydantic + SQLAlchemy)
        |
        | SQLite / PostgreSQL + Redis cache fallback
        v
Data Models + Audit + Task Artifacts
        |
        | embedded / external worker
        v
Managed AI Endpoint / Runtime Bridge / OpenClaw
```

和早期“纯前端 + Mock”阶段相比，当前阶段已经有以下关键变化：

- 核心业务数据全部进入数据库模型
- 登录、JWT、RBAC 已接通
- 任务执行从同步模拟推进为后台 Worker 异步执行
- Provider 不再是本地假数据，支持真实模型调用
- 前端多个页面已统一成即时反馈式操作台
- 网关已经覆盖 `chat/completions`、`responses`、`agents/run` 和对应 WebSocket 入口
- Runtime 已支持注册申请、激活码换长期凭据、命令轮询、授权、心跳和完成回传
- MCP 已通过 Server / Capability 策略和一次性执行票据进入执行链路
- Redis 缓存、入口限流、请求大小限制、Trusted Host、安全响应头和敏感字段脱敏已落地

## 4. 当前交互模型

当前前端交互不是传统“编辑一堆字段 -> 点击保存”，而是统一为两类模式：

### 4.1 即时反馈动作

适用页面：

- 技能管理
- 资产保护
- 安全事件
- 系统设置动作区

特征：

- 点击动作立即提交到后端
- 顶部反馈条实时显示 `saving / saved / error`
- 结果会同步回写列表或焦点卡片

### 4.2 元数据驱动表单

适用页面：

- 防御配置
- 资产白名单
- 技能信任状态
- 系统设置

特征：

- 后端下发 `field_meta`
- 前端根据 `control / options / tone / helper_text` 渲染控件
- 不再由前端写死 `log_level`、`notify_email`、`risk_level`、`trust_status` 等映射

## 5. 任务执行链路

当前最小闭环如下：

```text
创建任务
  -> 任务入库，状态 queued
  -> /attack-tasks/{id}/run 提交
  -> task_worker 后台线程或外置 Worker 取任务
  -> policy_enforcer 做预授权
  -> task_runner 组装 prompt / Runtime 命令 / Skill 扫描请求
  -> model_provider 或 Runtime bridge 执行
  -> 保存 raw_response
  -> 生成 SecurityEvent
  -> 生成 Report 与导出产物
  -> 任务置为 done / failed / scheduled / dead_letter
```

### 当前关键实现点

- `task_worker.py`
  - 负责释放到期 `scheduled` 任务、恢复陈旧 `running` 任务
  - 负责失败重试和 dead-letter 归档
  - 负责后台轮询与执行
- `task_runner.py`
  - 负责 prompt 构造、结果解析、事件和报告生成
- `model_provider.py`
  - 负责真实 Provider 调用，受管 AI 目标优先于 legacy `.env` Provider
  - 记录调用开始、成功、失败日志
- `mcp_security.py`
  - 负责 MCP allowlist、模板、票据签发、票据消费和工具结果校验
- `runtime_dispatch.py`
  - 负责 OpenClaw 运行时命令派发、领取、完成和过期回收
- `guard_trace.py`
  - 负责把授权、规则评估和 AI 复核字段整理到事件报告视图

### 当前边界

- Worker 可嵌入或外置，但仍是数据库轮询调度，不是 Redis / RabbitMQ 消息队列
- 运行中的上游 HTTP 请求仍是协作式中断，不是强制硬中断
- 本地 SQLite 在高强度写入并发下可能触发 `database is locked`，生产级并发验证建议使用 PostgreSQL
- 报告已支持 JSON / HTML / DOCX，但还没有 PDF、签章和对象存储生命周期管理

## 6. 日志与可观测性

当前本地开发模式已做统一日志收口：

- 应用生命周期：`app.lifecycle`
- 请求摘要：`app.http`
- Worker：`app.worker`
- 任务流水线：`app.pipeline`
- Provider：`app.provider`

后端本地启动入口：

```powershell
cd backend
python run_dev.py
```

这样 `uvicorn` 自身日志也能共用统一格式，不会和应用日志风格割裂。

## 8. 当前工程边界

### 8.1 仍偏原型的部分

- 报告导出已升级为 JSON / HTML / DOCX 真文件产物，但还没有 PDF 与签章版正式模板
- 系统动作已生成真实导出/备份文件，并提供系统工件列表与下载接口
- 已有样本 API、样本执行页面和批量建任务能力，但长时间大批量压测仍需要继续补强

### 8.2 工程化尚未补齐的部分

- 没有 Alembic 迁移
- 没有 CI/CD
- 没有独立任务队列
- 已收集 `57` 项后端测试；最近完整执行为 `56 passed, 1 failed, 4 warnings`，唯一失败来自 SQLite 在 `100` 并发 Skill 导入下的写锁竞争
- 还没有完整的前端端到端测试和 CI 自动化测试矩阵

### 8.3 安全能力尚未独立模块化的部分

- 当前没有独立 `security_engine/`
- 任务策略仍主要在 `task_runner.py` 内聚合
- Runtime 授权、心跳、完成回传和 OpenClaw 桥接已经落地，但更多第三方 Runtime 协议仍需继续标准化

## 9. 推荐的下一步工程演进

1. 引入 Alembic，解决表结构演进问题。
2. 将 Worker 调度从数据库轮询继续演进到 Redis / RabbitMQ 一类队列。
3. 针对高写入并发路径补充 PostgreSQL 压测、重试和事务收敛。
4. 扩展更多 Runtime / Adapter 协议，把 Dify、Coze、自研 Agent 接入统一运行时协议。
5. 将导出、备份、报告产物继续升级为更正式的 PDF / 签章式文件服务。

## 10. 一句话总结

当前项目最准确的工程描述是：

它已经完成了“前后端控制台 + 数据库主链路 + JWT/RBAC + 统一网关 + Runtime 联动 + MCP 票据 + Redis 缓存 + 后台任务执行 + 报告闭环 + 基本回归测试”的 Beta 原型搭建。下一阶段的重点不再是继续堆页面，而是把任务队列、高并发数据库验证、前端端到端测试和生产级运维能力真正工程化。
